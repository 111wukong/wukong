# 架构：它实际上是怎么运作的

这份文档讲的是**建成的系统**，不是设计期的设想。设计期的取舍记录在 [`design-review.md`](design-review.md)，那份回答「我们决定不做什么」；这份回答「每个部件为什么是现在这个形状」。

读它需要的背景：Python 3.11+，SQLite，零外部服务，约 2.5 万行源代码、74 个模块、1000 条离线测试。

---

## 0. 一条主张和四个后果

**主张：一个 agent 系统里，唯一不能妥协的是「它说的和它做过的必须一致」。**

这句话听起来像口号，所以它必须由结构来保证，而不是靠提示词。四个后果直接塑造了整个内核：

1. **状态是事件溯源出来的**，不是内存里的对象。崩溃、恢复、审计、重放，全是同一个问题的不同问法。
2. **工具调用是写前台账**，不是执行后记录。顺序不可交换：校验 → 策略判定 → 台账 → 执行 → 台账。
3. **每一条人工决策都是一个事件**。批准、拒绝、逐块收窄、改过的计划——不存在「只在进程里改一下」。
4. **完成是可以被质疑的**。模型说「做完了」之后，还有一道能跑项目自己检查的闸门。

下面四节是内核，第五节是三个闸门，其余是外围。

## 1. 事件溯源的状态机

### 1.1 结构

每个任务的所有事实构成一条**每任务连续、无空洞**的事件流（`storage/db.py` 的 `events` 表，主键 `(task_id, seq)`）。内存里的 `AgentState` 不是真相，它只是这条流的**折叠结果**——`agent/state.py` 的 `replay()` 是纯函数：给一串事件，还给一个状态。

这件事买来的四样东西，每一样都对应一种真实死法：

| 没有它会怎样 | 有了之后 |
|---|---|
| 进程在第 12 步被杀，任务卡在 `running`，没人知道它做了什么 | `wukong task resume <id>` 接着跑，事件流续写 |
| 「它到底改没改这个文件」只能靠翻 shell history | `wukong task events <id>` 逐条列出，含每次工具调用的台账行 |
| 审批只在内存里生效，崩溃后重放把人类拒绝的改动照写进去 | 审批、收窄、改计划全都是事件，重放得出同一结论 |
| 上下文压缩是一次对消息列表的「手术」，出错就丢状态 | 压缩是 `CONTEXT_COMPACTED` 事件，`replay` 重新折出来 |

任务表里存的是 `last_event_seq`、`status`、`pending_confirmation` 这类**投影**——为查询便宜，不作为真相。真相永远在事件里。

### 1.2 状态机

七个状态：`pending → planning → running ⇄ waiting_confirmation → completed / failed / cancelled`。

`waiting_confirmation` 是整个设计里最重要的一个状态：它意味着**任务停在一个等人的决定上，而不占用任何预算**。工具审批、计划批准都停在这里。它不是「错误」，是正常的一站。

### 1.3 中断的在途调用：本项目最核心的语义

进程在「即将执行 `git commit`」和「已执行 `git commit`」之间死掉，恢复时怎么办？这是每个 agent 框架都迟早要回答、而大多数选择不回答的问题。

本项目的答案由台账的行内状态给出（`agent/executor.py` + `storage/store.py`）：

| 台账行状态 | 含义 | 恢复时的处理 |
|---|---|---|
| `started`（未结束） | 执行前落库，执行后未知 | 按工具的幂等性分流 |
| 工具的 `idempotent=True` | 读文件、查询 | 重跑，新结果交给模型 |
| 工具的 `idempotent=False` | **所有 shell 命令** | 标记 `ambiguous`，**不重跑**，往上下文写一条明确警告：「这次调用的结果未知，可能已生效。先核实当前状态再继续。」 |

非幂等调用**绝不产生第二行台账**——这是 `tests/test_resume_semantics.py` 断言的硬约束。选择「不重跑并说明」而不是「重跑试试」，是因为静默重复执行的破坏（重复提交、重复部署、重复发消息）比明确不知道大得多，而且前者在测试里永远绿。

## 2. 权限：六个效果类别，三个决定

### 2.1 为什么按「效果」而不是按「工具名」分类

权限清单写成 `allow_tools: [read_file, grep]` 是个陷阱：加一个新工具，或者模型用 `run_command cat x` 冒充「读」，清单就失效了。所以分类的轴是**一次调用能对世界做什么**（`types.py` 的 `EffectClass`，从无害到危险）：

```
read_only → write_local → execute_local → network → external_side_effect → system_admin
```

工具声明自己的效果类别；`run_command` 是 `execute_local`，无论命令是什么。决定是三个之一：`allow / confirm / deny`。

三个设计细节值得知道：

- **`confirm` 是一个状态，不是一个弹窗。** 它把任务停进 `waiting_confirmation`，把决定权交给 whoever 在看着（控制台、CLI、或者一个预授权的额度）。一个无人值守的运行可以在启动时声明 `--approve write_local`，把某一类以下全部放行——这是**额度**，不是绕过。
- **拒绝计数有上限。** 连续拒绝达到 `denial_limit`（默认 3）任务停止。这是防「模型被拒绝后换个写法再试」的循环。但**拒绝一个计划不计入**：「换个计划」不是「你不许做这个」。
- **执行前重新验指纹。** `agent/execution_identity.py` 在批准时给「工具 + 参数 + 工作区」取指纹，执行前重取并比对。批准之后参数被换掉，调用会被拒。这一条挡的是「批上帝许可，然后用在别处」。

### 2.2 沙箱

`run_command` 在 macOS 上包 seatbelt（`sandbox/`），失败时**降级并明说**：`wukong sandbox` 报告隔离到底生效没有。谎报隔离比没有隔离更糟——用户会以为命令跑在一个笼子里。

## 3. 上下文：预算是显式的，压缩是主动的

「跑了 8 步，第 12 步 provider 返回 400，整个任务丢失」是这类系统最常见的死法，因为 `run_command` 的输出轻松上二十万字符。

`agent/context.py` 的做法：

**消息列表每步从状态重建**，不是 append。这让压缩成为状态的纯函数，而不是对一条不断变长的列表做手术。

**两条独立的花钱路径，分开算：**

- **装不装得下**——`budget()` 是模型窗口减输出预留；渲染时把日志按剩余预算截断（`tool_output_chars` 默认 8000，每条日志再按比例分）。这一步免费，不需要模型。
- **状态是否无限增长**——`should_compact()` 看的是**原始日志**的 token 数超过 `compact_at_ratio`（默认 0.3）乘预算。压缩把日志折成 `compacted_summary` 并丢弃原文，保留最近 `keep_recent_observations`（默认 6）条。

注意这两个阈值量的不是同一个东西：前者量渲染后的 prompt，后者量可持久化的状态。用后者问前者会永远不压缩，状态无上限；用前者问后者会过早摘要，丢掉细节。

**压缩永远不能失败一个任务。** 没有便宜的摘要模型时降级为结构化摘要（`_digest`/`_merge`），摘要调用抛异常同样降级。一个任务不应该因为少配了一个模型别名而变得不可完成。

## 4. 三个闸门：它们各自挡的是什么

三个闸门在 README 里是卖点，在这里讲机制。

### 4.1 逐块审查：写前台账换来的能力

普通 agent 的审批是「一段 diff 加一个批准按钮」——那是把「扫一眼然后点」伪装成审查。一个五文件的改动和一个错别字，用的是同一个 Yes/No。

本项目的审批拿到的是 `changeset`：文件 → hunk → 带双行列号的行（`review.py` 解析并重建）。取消勾选的 hunk **不会被写入**。

```
只接受 h0：写入 = before + h0，h1 不在文件里
```

这能做，**只因为台账是写前的**。待批准的调用还只是一个 `content` 字符串，「只接受这些块」就是换一个字符串，没有半写状态需要回滚。对比之下的 checkpoint 类实现只能先写再回滚，而且要额外处理「回滚了文件但没回滚对话」。

收窄本身是一个事件（`CONFIRMATION_REVISED`），然后才是 `CONFIRMATION_GRANTED`。不是内存里的一次修改：`resume` 从事件重放状态，只活在进程里的修订会在崩溃后消失，而重放会把人类刚刚拒绝的 hunk 全部写进去。

未知的 hunk id 是 **400**，不是「忽略它」。一个说「只要 h0」的批准被悄悄当成「全部」，是审批闸门能发生的最坏失败模式。

### 4.2 计划批准：唯一能在花钱之前省钱的闸门

工具审批在模型已经决定怎么做之后才触发；预算在钱花完之后才说话。最贵的错误不是「跑错了」，是「正确地跑错了方向」，而此前没有任何东西能拦它。

`agent.require_plan_approval` 让运行在规划完成、第一个工具调用之前停下来。复用的是同一个确认容器（`PendingConfirmation.kind = "plan" | "tool"`）——停下来、询问、记录、恢复是同一副骨架，两套机制意味着两处可能把 resume 语义做错。

批准时提交的是**编辑后的清单**，它成为契约（`PLAN_APPROVED` 事件里存的就是它，`replay` 据此折出 `state.plan`）。拒绝清空计划让循环重新规划，并把人的原话写进日志；它**不计入拒绝计数**。

### 4.3 验证闭环：完成前先跑一遍

`agent.verify_command` 配一条命令（默认空 = 不验证）。规则只有一条：**模型说要完成时，如果这次运行写过文件而还没验证过，先跑它**。

- 通过 → 正常完成。
- 失败 → **不完成**。输出的**尾部**（测试框架把失败放末尾；截头会保住标题丢掉断言）作为 system 记录回灌，循环继续。
- 连续失败到 `verify_max_rounds`（默认 2）→ 允许结束，但记下「仍然失败」，任务视图挂一个红标记。

它**不经过权限引擎**，理由要能站住：命令来自用户自己的设置，不是工作区、不是模型，所以它继承用户 shell profile 的信任级别——一个仓库不能靠被 clone 就把命令塞进你的运行里。反过来把它挂到模型的 `execute_local` 额度上，等于用户在自己配置里写了命令、还要额外把 shell 权限交给模型才能用。配套约束：一条命令，没有 shell（`&&` 会被拆成参数）。

这条路上踩到过一个真 bug，值得记住：**审批通过的调用在 `resume()` 里执行，不走 `_run_tool_calls`**，所以只在那一条路径上记录「刚写过什么」的话，「一个文件、一次审批」这种最常见的运行永远不会被验证。

### 4.4 同行审查：一个只读子 Agent 的咨询意见，不是第四道闸门

闸门的代价是「人要看」。子 Agent 之间互相把关（「互相」）的目的不是省掉这道闸，而是把人的注意力引导到更值得看的地方：在人工审批之前，先让一个**只读**的子 Agent 把待写变更集读一遍，给一句咨询意见。

它从 `review.py` 已经解析好的 `changeset` 出发，渲染成一段人类可读的简报（路径 + 每块的增减标记），交给一个全新的 `AgentRuntime`。这个审阅者的权限引擎是**只许读、其余一律拒绝**（`peer_review.py` 的 `_reviewer_engine`）：它因此永远不会自己停下（`confirm` 只属于写/执行的决定）、永远不会写共享状态、也不会在父任务里递归——它就是一个跑完即焚的建议生成器，天然卡不死父任务。

审阅者必须回一段带 `[verdict]` / `[concerns]` / `[summary]` 的结构化文本。**解析失败时降级为 `changes_requested`（fail open 朝向人类注意），绝不静默放行**：缺 `[verdict]`、措辞不认识、审阅者没跑完，结果都是「建议人再看一眼」，而不是「看起来没问题」。三种结论是 `approve` / `changes_requested` / `blocked`，并且**只是建议**——它不增减人类的批准/拒绝权力，人类照样可以无视。

它尊重逐块审查的 `reviewable` 标记：纯命令确认、非变更集确认不经过它。结果通过 `PEER_REVIEW_COMPLETED` 事件落库（只带 verdict 字典，不含审阅者的完整对话），并挂在 `PendingConfirmation.peer_review` 上随确认容器一起走到 AG-UI 协议和 `/api/v1/tasks/{id}/review`，由控制台渲染成一张咨询卡片。

默认关闭（`peer_review.enabled = False`）。开着时只多一次只读模型调用，不碰写权限、不影响现有三道闸。

## 5. 周边：技能、多 Agent、工作流、互操作

**技能（`skills/`）**：`SKILL.md` 带 frontmatter，元数据清单只进上下文（每个约 100 token），模型显式 `load_skill` 才拿全文——渐进披露，不是把三十个技能全文塞进系统提示。技能有自己的生命周期 `candidate → validated → approved → active → deprecated`，每一级都是人工决定：**agent 不能自己升级自己的技能**，这是写进状态机的闸门，不是提示词里的请求。

**多 Agent（`orchestration/multi_agent.py`）**：`delegate` 工具把子目标派给真实子任务，并发跑、各自有事件流和预算。父任务的流只携带摘要（`SUBAGENT_*` 事件），子任务的细节在子任务自己的 id 下——父流假装能装下细节，就会多出一份更薄、迟早和真相不一致的视图。要看真实的分叉与每个分支自己的预算，用 `wukong task tree <id>`：它从任务投影（而非事件流）重建 parent→child 树，所以不重放事件，也和 `task show` 同源。同一棵树也通过 `GET /api/v1/tasks/{id}/tree` 暴露给 HTTP 客户端，`--json` 与它同形。控制台侧栏的父任务行直接显示子树合计——用已经取到的行在客户端聚合，不额外请求，所以它和 `task tree` 报的是同一个数。

**工作流（`orchestration/workflow.py`）**：YAML 声明式编排，节点是任务或表达式，加载时校验引用（悬空引用在加载期就炸，而不是跑到第三步）。工作流运行本身也是一个任务。

**A2A（`a2a/`）**：发布 Agent Card、接任务、做服务端。签名和鉴权在 `security.py`。

**AG-UI（`api/agui.py`）**：前端消费的是协议事件，不是内部状态。控制台因此可以整个换掉（包括换成 CopilotKit 的 React 组件）而不用碰后端。

## 6. 它不做什么

一份架构文档不写短处，就没人能判断它写的长处。

- **不是编辑器**。没有内联 diff，没有 IDE 集成。赌注在运行时：跑在别人机器上、CI 里、关掉窗口之后，闸门才是唯一兜得住的东西。
- **不自己训练或微调任何东西**。记忆是抽取+检索（`memory/`），技能是人工批准的文档。
- **不假装沙箱无处不在**。macOS 有 seatbelt，别处降级并明说。
- **不做「反思一步、评估一步」的循环**。反思只在任务结束做一次（且默认关，因为它花一次模型调用）。AutoGen 式的每步反思 token 成本高一个数量级，而本项目把这份预算花在验证和压缩上。
- **并发上限是一个进程**。多任务是并发跑的，但都活在同一个 runtime 实例里；跨进程的任务协调不存在，也没有假装存在。

## 8. 用真实模型验证过一次

1000 条测试全是 mock 驱动的，所以有一件事它们证明不了：闸门在真实 token 流下的表现。2026-10-18 用 DeepSeek（`deepseek-chat`）对一个带真实 bug 的项目跑了一次完整链路，结论是可以放心的那类：

```
计划门停下 → 批准 → 只读调用不再询问 → 写入停下（变更集 +1 −1，就是那一行）
→ 批准 → 模型自己跑测试（4 passed）→ 校验命令自动通过（exit 0）→ completed
```

7 步、41423 token、$0.0123。两个细节值得记住：

- **模型选择了 `apply_patch` 而不是 `write_file`**，而逐块审查只对后者开放（`partial: False`，全有或全无）。这是自洽的：一个编辑本来就是意图的单位，而「部分接受一个编辑」没有明确语义。
- 校验命令指定的解释器路径带空格、命令从未执行时，模型**如实报告了失败**，没有粉饰，也没有试图改掉这条检查。这正是这个闸门存在的目的。

同一次运行抓出两个真 bug，都已修（`config.py` 的部分权限覆盖、`shell.py` 的退出码缺失），见 `tests/test_config_round_trip.py::TestPartialPermissionOverrides` 与 `tests/test_tools.py::TestFailedCommandsCarryAnExitCode`。

复跑时又暴露一个：**`run_tests` 在无 venv 的工作区根本跑不起来**——回退到裸 `pytest`，而清洗过的子进程 PATH 上没有它，于是「用来跑测试的工具」以 `command not found` 收场，模型只好退回 `run_command`（恰恰是它文档里让它别做的事）。现在回退链是：项目 venv 的 pytest → venv 自己的 `python -m pytest` → **运行中的解释器**（`pip install -e ".[dev]"` 就是把 pytest 装在那里）。修完之后复跑，`run_tests` 成为任务的第一步并真的跑了起来（exit 1 = 找到了那个失败，这正是它该做的事）。

值得记的是修这次时自己先写错了一版：`if "pytest" in argv` 是**成员判断**不是子串判断，`"pytest" in ["/x/.venv/bin/pytest"]` 是 False，导入路径被静默跳过，收集阶段以一个「看起来像测试文件坏了」的 ImportError 死掉。一个**真的执行工具**的既有测试立刻抓住了它——这就是为什么那个测试值得存在。

## 9. 测试策略

1000 条测试，全部离线，不需要 API key。分三类，各自守不同的东西：

- **语义测试**（`test_resume_semantics.py`、`test_verify.py`、`test_plan_approval.py`、`test_review.py`、`test_peer_review.py`）断言的是「崩溃/拒绝/收窄/同行审查之后，状态折出来是什么」。它们用脚本化模型驱动真实 runtime，写真实文件。
- **接口测试**（`test_api.py`、`test_attachments.py`）断言 wire 格式：SSE 事件、`/agui` 载荷、附件路由。
- **接线测试**（`test_wiring.py`、`test_console_wiring.py`）断言「每个能力位都有读者」「每个 DOM id 都存在」。它们存在的理由很具体：`vision` 曾经是一个没有任何人读的能力标志——这类 bug 单测抓不到，因为没有任何行为可断言。
